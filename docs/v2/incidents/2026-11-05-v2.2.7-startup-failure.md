This is a blameless review. It describes what the system allowed to happen, not who did what.

## Impact

Launching the V2.2.7 Portable EXE showed this dialog and exited:

> PcNinja WinUpdate Tool portable failed to start:
> Exception setting "OutputEncoding": "The handle is invalid."

The UI could not be used at all from the Portable EXE. The installed GUI host runs the same code path, so it is expected to fail the same way. Command-line and scheduled use kept working.

## Timeline

- **2026-10-31**: V2.2.7 is released to fix Hebrew update titles showing as mojibake. Commit `e5ff9b8` adds `Set-PcnUtf8ConsoleEncoding` and calls it at the start of every `WinUpdateTool.ps1` run.
- **2026-11-05**: The startup failure is reported with a screenshot of the error dialog.
- **2026-11-05**: Root cause found. The fix and the V2.2.8 version bump are merged (JavierTorresFelendler/PcNinja-WinUpdateTool-V2#10).
- **2026-11-05**: Windows CI added. Its first run confirms the fix on a real Windows runner: the no-console regression test passes, the package build succeeds, and the Portable EXE runs without a console (JavierTorresFelendler/PcNinja-WinUpdateTool-V2#11). VM testing passes.
- **2026-11-05**: V2.2.8 is published through the new Release workflow.

## Root cause

```powershell
function Set-PcnUtf8ConsoleEncoding {
    $utf8 = New-Object System.Text.UTF8Encoding($false)
    [Console]::OutputEncoding = $utf8      # throws when no console exists
    $global:OutputEncoding = $utf8
}
```

1. On .NET Framework, assigning `[Console]::OutputEncoding` calls the Win32 `SetConsoleOutputCP` API. With no console attached to the process, that call fails with `ERROR_INVALID_HANDLE`, and .NET throws `IOException: The handle is invalid`.
2. The Portable launcher (`packaging/PortableLauncher.cs`) and the installed GUI host (`packaging/WinUpdateToolHost.cs`) are built as `/target:winexe`. A GUI-subsystem process has no console, and both hosts run `WinUpdateTool.ps1` **in-process** in a PowerShell runspace.
3. `WinUpdateTool.ps1` sets `$ErrorActionPreference = 'Stop'`, so the exception is terminating. The launcher catches it and shows the error dialog.

## Why it was not caught before release

- **The test ran in a console.** The V2.2.7 Pester test called the helper from a console host, where the assignment succeeds. The test covered the function but not the hosting condition that the shipped GUI runs in.
- **No automated Windows build or run.** Packages were built and published by hand, and nothing launched the built EXE before release.
- **Platform behavior was not obvious.** A line that only sets an encoding fails depending on the process type that runs it. The failure is specific to .NET Framework and the Windows GUI subsystem, and invisible in any console.

## Fix (V2.2.8)

- `$OutputEncoding` (process-local, always safe) is set first.
- `[Console]::OutputEncoding` is set inside `try/catch`. Without a console there is no console output to encode, so skipping it changes nothing. Wherever a console exists, the V2.2.7 UTF-8 behavior is unchanged, so the Hebrew rendering fix still applies.
- This matches the pattern in `Win-Upgrade-Tool-by-PcNinja`, which sets `Console.OutputEncoding` only in console contexts (`CliRunner.cs` and PowerShell child processes), never in the GUI.

## Lessons

- **Code that runs inside a GUI host must not assume a console.** Any `[Console]::*` setter, `Console.Out` handle, or `$Host.UI.RawUI` call can fail there. Guard it, or scope it to console entry points.
- **Test under the conditions the product ships in, not the conditions the test runner happens to have.** Here that meant a process with no console.
- **The fastest release check is to run the built artifact.** A two-minute CI job that starts the EXE would have blocked this release.
